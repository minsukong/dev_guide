# 백엔드 개발·검토 기준

요구사항·설계·구현·리뷰에서 필요한 절만 선택한다. 언어·프레임워크·DB·인증 방식은 실제 저장소와 합의된 계약을 따른다. 아래 항목은 모든 기능에 일괄 적용할 체크리스트가 아니라 변경에 따라 확인할 판단 기준이다.

<a id="scope"></a>
## 범위와 기존 시스템

- 대상 서비스·모듈·호출자·데이터 소유자·실행 환경을 확인한다. 빌드 설정, 의존성, 실제 코드, API 정의와 스키마에서 현재 동작을 읽는다.
- 확인된 요구, 기존 구현, 기술 제안, 미정을 구분한다. 기존 코드와 문서가 충돌하면 관련 경로·버전/확인 날짜·차이·영향을 기록한다.
- 작업 범위 밖의 정책·운영 이슈를 자동 blocker로 확대하지 않는다. 반대로 필수 선행 조건을 임시 값으로 숨기지 않는다.

<a id="project-docs"></a>
## 권장 확장 — 프로젝트 docs 운영

기능과 참여자가 늘어나면 업무 규칙·API 계약·데이터 설계·실행 방법을 프로젝트 docs로 정리해 개발자와 AI가 함께 참조하는 방식을 권장한다. 같은 내용을 매번 설명하는 부담을 줄이고 새 작업·담당자 변경에도 기준을 이어가기 위한 확장이다. 공용 가이드는 작업 방법을, 프로젝트 docs는 해당 프로젝트의 지식을 담당한다.

처음에는 기획 자료·소스·작업과 결정 기록으로 시작하고 반복해서 쓸 내용부터 정리한다. 기존 문서가 있으면 기준 위치와 관리 담당을 재사용한다. 문서 목차와 필요한 절을 AI에 연결하고 실제 코드·설정·검증 결과와 대조한다. 규칙·계약·실행 방법이 바뀌면 관련 문서를 같은 변경 흐름에서 갱신하며, 미정·현행·합의된 목표와 남은 갱신 항목을 구분한다.

문서 종류별 예시, 추천 폴더 구조, 작업→검증→문서 갱신→다음 작업의 운영 흐름과 AI 요청 예시는 [프로젝트 docs 운영 안내](project-docs.md)에 있다. 폴더 이름·구조는 예시이며 실제 저장소와 팀의 공유 기록 위치에 맞춰 필요한 부분부터 적용한다.

<a id="ppt-input"></a>
## PPT로 전달받은 기획서 읽기

PPT(.ppt·.pptx)로 기획서를 받으면 파일을 AI에 첨부하거나 작업 폴더의 경로를 지정한다. 공유 링크를 사용할 때는 AI가 해당 파일에 실제로 접근할 수 있는지 확인한다. Figma(기획서) 연결이나 API 토큰은 PPT 파일을 읽기 위한 전제가 아니다.

1. 검토 기준을 지정한다. 파일명·버전, 대상 기능, 슬라이드 번호·제목을 전달한다. 여러 파일이 있으면 최신 승인본과 참고본을 구분하고 화면 정의서·API 명세 등 함께 볼 근거를 연결한다. 번호가 바뀔 수 있으므로 슬라이드 제목·대상 영역도 기록한다.
2. 처음에는 목차와 전체 기능 흐름을 파악하고, 이번 기능과 전후 흐름에 필요한 슬라이드를 읽는다. 긴 기획서는 기능별로 나누고 확인한 정책·미정·출처를 기록해 다음 검토에 이어간다. 파일 전체를 한 번에 전달해도 모든 내용이 컨텍스트에 계속 유지된다고 가정하지 않는다.
3. 본문·표·발표자 노트 등 읽을 수 있는 자료를 확인한다. 화면 캡처·도형·화살표·상태 분기는 슬라이드 이미지나 렌더링 결과를 함께 봐야 한다. 텍스트 추출만 성공한 경우 화면 배치·흐름까지 확인 완료로 기록하지 않는다. 숨김 슬라이드나 이전 버전의 내용은 현행 요구인지 확인한다.
4. 읽기 실패나 일부 추출이면 실패한 파일·슬라이드·정보 종류를 남긴다. 도구가 .ppt를 지원하지 않으면 원본을 보존하고 .pptx 또는 PDF 사본을 받아 검토한다. PDF·캡처로 대체하면 원본의 발표자 노트·상호작용·누락된 슬라이드는 미확인으로 남긴다. 파일이 열렸다는 사실과 기획 내용을 읽었다는 사실을 구분한다.
5. 기능 흐름에서 업무 규칙·상태 전이·데이터·권한·API 요구·예외 처리를 도출한다. 화면에 없는 오류·동시 요청·재시도·취소·운영 조건은 기존 정책·계약에도 답이 있는지 찾고, 확인된 내용과 담당이 정해야 할 질문을 분리한다. 화면 문구만으로 endpoint·DB 스키마를 확정하지 않는다.
6. 결과에는 검토한 파일·버전·슬라이드, 확인된 요구, 누락·충돌·미정, 개발 영향과 진행 가능한 범위를 남긴다. 미정은 결정 기록에 연결하고 담당·근거·재개 조건을 관리한다. 읽지 못한 자료를 기획 누락으로 단정하지 않는다.

AI 요청 예시:

```text
기획서: <첨부한 PPT 또는 파일 경로·공유 링크>
기준: <파일명·버전 / 최신 승인본 여부>
검토 범위: <대상 기능 / 슬라이드 번호·제목 / 관련 전후 흐름>
lounge-grill로 백엔드 요구사항을 검토해줘.
본문·표·화면 이미지·읽을 수 있는 발표자 노트를 확인하고, 읽지 못한 범위는 알려줘.
업무 규칙·상태·데이터·권한·API·예외 처리에서 확인된 내용과 결정할 질문을 구분해줘.
근거는 파일·슬라이드별로 남기고, 개발 영향·진행 가능한 작업도 정리해줘.
아직 구현하지 마.
```

## Figma(기획서) 읽기 연결과 접근 오류

기획 자료를 직접 확인해야 할 때 적용한다. 구체적인 기술·DB 작업에 불필요한 Figma(기획서) 읽기를 강제하지 않는다. 실제 연동 설정은 개인 하네스에서 관리하고, 개발자용 순서는 [안내의 시작 절](../index.html#purpose)에 있다.

1. 사용 가능한 연결이 공식 Desktop MCP, 공식 Remote MCP, REST API 직접 조회 중 무엇인지 확인한다. 연결 이름만으로 실제 호출 경로를 추정하지 않는다. 공식 MCP가 연결돼 있으면 해당 읽기 도구부터 확인한다.
2. 화면·프레임 링크 또는 메뉴·기능 전체 링크와 검토 범위를 받는다. 작은 변경은 관련 화면과 전후 흐름부터 읽고, 전체 메뉴 검토는 아래 범위·컨텍스트 기준에 따라 구조 확인과 상세 검토를 나눈다. 처음 연결할 때는 작은 화면 하나로 실제 읽기부터 확인한다. Remote MCP에는 대상 링크를 제공하고, Desktop MCP의 현재 선택 읽기는 해당 도구가 지원할 때 사용한다.
3. Desktop MCP는 데스크톱 앱에서 Dev Mode와 MCP 서버를 켜고 AI 도구를 연결해야 한다. Remote MCP는 데스크톱 앱 없이 계정 로그인·접근 허용으로 연결하며 일반적인 설정에 개인 토큰을 따로 전달하지 않는다. 파일 접근권한·지원 도구·계정 좌석·사용 한도는 선택한 경로에서 확인한다.
4. REST API는 인증·파일 접근권한·scope가 필요하며 조회 한도는 좌석·endpoint·파일이 속한 플랜의 영향을 받는다. 403은 권한·인증 범위 등을, 429는 사용 한도와 Retry-After를 확인한다. 재시도 시간이 길거나 할당량이 부족하면 반복 호출하지 않고 담당과 접근 조건을 확인한다.
5. MCP에도 플랜·좌석에 따른 읽기 도구 한도가 있다. REST API를 내부에서 호출하는 도구라면 그 경로의 제한도 확인한다. MCP라는 명칭을 REST 제한 회피의 근거로 쓰지 않는다.
6. 결과가 크거나 일부만 반환되면 요청 범위를 줄여 필요한 화면·설명만 읽는다. 제공된 도구가 주석·프로토타입 등 필요한 자료를 지원하는지도 확인한다. 접근 실패·응답 일부·연결 성공만으로 기획 전체를 읽었다고 보고하지 않는다.
7. 읽기 실패 시 방식·대상·오류·확인한 범위·필요한 조치를 남긴다. 내보낸 PDF·화면 캡처·기획 설명으로 검토를 계속할 수 있지만, 전달받지 못한 화면·주석·흐름은 미확인으로 표시한다. 토큰은 연결 도구의 인증 설정 또는 실행 환경의 비밀값으로 제공한다. AI에는 설정 위치·변수명·사용 방식을 전달하고 값은 출력하지 않는다. 개인 토큰으로 REST API를 직접 호출하면 X-Figma-Token 헤더를 사용한다. FIGMA_ACCESS_TOKEN은 예시 변수명이며 실제 도구가 읽도록 연결해야 한다.

공식 문서 확인: 2026-10-28. 수치 한도는 바뀔 수 있어 고정 규칙으로 복제하지 않는다. [REST API 제한](https://developers.figma.com/docs/rest-api/rate-limits/) · [인증](https://developers.figma.com/docs/rest-api/authentication/) · [오류](https://developers.figma.com/docs/rest-api/errors/) · [MCP 접근·제한](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/) · [Desktop 연결](https://developers.figma.com/docs/figma-mcp-server/local-server-installation/) · [Remote 연결](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/). 문서 본문은 내부 기준으로 사용할 수 있고 공식 URL은 변경 시 확인할 참고 자료다.

## 링크 범위·사용량·컨텍스트

- 화면·프레임 링크는 특정 동작·API 요구·작은 변경의 확인에 적합하다. 전후 흐름·공통 정책이 빠질 수 있으므로 관련 근거가 필요한 범위는 함께 확인한다.
- 메뉴·페이지·섹션·파일 링크는 기능 전체 흐름을 파악할 때 사용한다. 파일 링크만으로 검토 범위를 추정하지 않고 대상 메뉴·목적을 확인한다. 먼저 가벼운 구조·화면 목록을 확인하고, 관련 화면 묶음별로 상세 자료를 읽는다. 가능한 도구에 구조 조회 기능이 있으면 활용한다.
- 전체 메뉴 검토가 요청됐다면 작은 범위로 임의 축소해 끝내지 않는다. 묶음별로 순차 검토하고 확인·미확인 범위와 근거 링크를 기록한 뒤 마지막에 화면 간 흐름·정책을 대조한다. 목록 확인만 한 상태를 전체 검토 완료로 쓰지 않는다.
- 비용과 시간은 링크 길이가 아니라 실제로 읽은 자료·이미지·도구 응답과 재조회량에 영향을 받는다. Figma(기획서)의 MCP/API 호출 한도와 AI 토큰·사용량, 컨텍스트 한도는 구분한다. 큰 범위라고 항상 같은 비용이 발생하거나, 노드를 나누면 이미 소진된 호출 한도가 복구된다고 가정하지 않는다.
- 컨텍스트는 현재 판단에 참고하는 대화·지침·코드·기획 자료·도구 응답의 범위다. 과도한 자료는 처리량을 늘리고 필요한 조건의 누락을 유발할 수 있다. 한도와 요약·잘림 방식은 도구·모델에 따라 다르므로 이전 자료가 모두 그대로 유지된다고 가정하지 않는다.
- 묶음마다 읽은 노드 링크·핵심 정책·미정·다음 검토 범위를 작업·결정 기록에 남긴다. 긴 작업을 이어갈 때는 해당 기록과 필요한 원문만 다시 확인한다. 요약을 원문 근거의 대체물로 취급하지 않는다.

개발자용 비교와 요청 예시는 [가이드 도입부](../index.html#figma-link-scope), 큰 범위 처리의 공식 설명은 [Figma(기획서) 공식 문서](https://developers.figma.com/docs/figma-mcp-server/avoid-large-frames/)를 참고한다.

## Figma(기획서)에서 도메인 요구 도출

- 관련 화면·주석·프로토타입과 기존 결정을 확인하고 노드·확인 날짜·관찰 범위를 남긴다. 과거 시안·회의 메모를 현재 기준과 구분한다.
- 행위자·권한, 조회/변경할 데이터, 업무 상태·전환 조건, 성공·실패·취소·만료·재시도에서 서버가 보장해야 할 동작을 찾는다.
- 화면 필드를 곧바로 테이블 컬럼이나 응답 필드로 옮기지 않는다. 표시용 값, 파생 값, 외부 데이터, 저장해야 할 업무 데이터를 구분한다.
- 근거에서 찾지 못한 항목은 미확인 또는 충돌로 남기고 실제 상황·결정 담당·영향받는 API/데이터/테스트·재개 조건을 질문한다. 접근하지 못한 자료는 확인한 것으로 쓰지 않는다.

<a id="domain"></a>
## 도메인 규칙과 상태 전이

- 행위 주체와 소유권, 식별자, 허용 상태 전이, 항상 유지해야 할 조건을 정의한다. 검증 위치와 실패 시 동작을 연결한다.
- 시간·기간·만료·취소·중복 처리·금액 계산 등이 기능에 영향을 준다면 기준 시각·단위·경계 조건을 확인한다. AI가 업무 기본값을 임의 확정하지 않는다.
- 결정된 업무 규칙 안에서 모델·서비스 경계와 책임을 설계한다. 기술 설계의 선택 근거를 기록하되 모든 내부 선택을 기획 승인 대상으로 돌리지 않는다.

## API 계약과 호환성

- 호출자, endpoint/메서드, 요청·응답 의미, 필수/선택/null·식별자·타입, 오류 코드·상태를 정의하고 관련 소비자와 계약을 확인한다.
- 인증·권한, 검증 실패·리소스 없음·상태 충돌을 구분한다. 페이지네이션·정렬·필터·수정 범위는 실제 사용 요구와 기존 규약에 맞춘다.
- 요청 반복·타임아웃·취소의 의미와 멱등성 필요 여부를 확인한다. 요청 키의 범위·동일 요청 판단·저장 기간이 필요한 기능이면 명시한다.
- 변경은 기존 호출자·버전·배포 순서·호환 기간에 미치는 영향을 확인한다. 초안·합의된 계약·실제 구현을 구분한다.

<a id="persistence"></a>
## 데이터 모델·트랜잭션·동시성

- 데이터 소유자, 식별·관계·고유성·참조 무결성, 삭제·보존과 이력 요구를 확인한다. 실제 조회·변경 경로에 맞게 스키마와 인덱스를 검토한다.
- 하나의 업무 변경에서 함께 성공·실패해야 할 범위를 정한다. 상태 변경·수량/권한 차감·이력 기록이 분리될 때 발생할 수 있는 불일치를 검토한다.
- 같은 자원에 대한 동시 요청·재시도·중복 이벤트에서 유지할 불변 조건을 정한다. 실제 DB와 처리 경로에 맞는 제약·원자 연산·잠금·버전 확인 등의 방법을 선택하고 경합을 검증한다.
- 스키마 변경은 기존 데이터와 구버전 코드에 미치는 영향, 이행 순서·데이터 보정·실패 시 복구를 확인한다. 운영 DB 변경을 개발용 검증과 혼동하지 않는다.

<a id="security"></a>
## 인증·인가·개인정보

- 주체 식별, 리소스·조직/테넌트별 접근 범위, 관리자 권한을 서버에서 검증한다. 클라이언트가 전달한 사용자·소유자 ID를 그대로 신뢰하지 않는다.
- 토큰·세션의 검증과 만료·재인증·폐기 동작은 기존 인증 구조와 계약을 따른다. 비밀값·개인정보를 코드·예시·로그에 노출하지 않는다.
- 외부 입력과 콜백·서명·파일/URL 등의 신뢰 경계를 확인하고 해당 기능의 검증 책임을 정한다. 감사 이력은 업무상 필요한 항목과 민감 정보 범위를 구분한다.

<a id="integration"></a>
## 외부 시스템·이벤트·실패 처리

- 외부 호출·이벤트·콜백의 책임자, 요청/응답·인증·식별자·오류와 확인 가능한 테스트 환경을 정한다.
- 타임아웃·재시도·중복·역순·유실·부분 실패가 해당 흐름에 미치는 영향을 확인한다. DB 변경과 외부 호출이 동시에 성공하지 않을 때의 업무 상태·복구 책임을 정의한다.
- 지연 처리·보상·재처리·메시지 저장이 필요하다면 기존 인프라와 업무 보장을 기준으로 설계한다. 요구 근거 없이 큐·새 서비스·추상 계층을 추가하지 않는다.
- 외부 시스템·소비자 계약을 대신하는 Mock·fixture는 합의된 범위·데이터·한계를 기록한다. 확인된 업무 규칙과 계약으로 단위 테스트용 stub·fake를 만드는 것은 개발자의 검증 설계이며 별도 업무 승인을 전제로 하지 않는다. 새 정책·외부 응답을 임의로 만들어 넣거나 이를 실제 연동 근거로 사용하지 않는다. 대체물 검증과 실제 외부 시스템 연동 검증을 구분한다.

<a id="operations"></a>
## 변경 영향과 운영 확인

- 실제 호출자·공유 모듈·테이블·배치·이벤트 소비자를 따라 변경 영향을 확인한다. 기존 클라이언트와의 호환성, 캐시·성능·실행 비용은 변경에 해당할 때 확인한다.
- 장애를 추적할 식별자·로그·관측 항목과 재처리·복구 수단을 관련 범위에서 정한다. 로그에는 실제 비밀값이나 불필요한 개인정보를 남기지 않는다.
- API·스키마·배치·설정의 반영 순서, 롤백 또는 전진 복구, 필요한 운영 협의를 기록한다. 배포·운영 변경은 실제 요청된 권한과 범위에서 실행한다.

<a id="verification"></a>
## 테스트·리뷰·완료 근거

- 단위 테스트는 업무 규칙·상태 전이·경계 조건을, DB 통합 테스트는 제약·트랜잭션·rollback·경합을, API 테스트는 권한·입출력·오류 계약을 검증하도록 선택한다.
- 외부 연동 변경은 타임아웃·중복·실패·재처리를 필요한 환경에서 확인한다. 마이그레이션 변경은 실제 엔진·버전·데이터 조건과 관련 호환성을 확인한다.
- 위 검증을 매번 전부 요구하지 않는다. 실제 저장소의 빌드·정적 검사·테스트 명령 중 변경 영향에 필요한 것을 실행하고, 기존 실패와 새 결함을 구분한다.
- 검증 대상·환경·명령·결과(Pass / Fail / Not Run / N/A)를 [작업 기록](task-template.md)에 남긴다. 대체 DB·Mock·미실행 환경은 한계를 명시한다.
- 필수 완료 조건이 충족되었는지 확인하고 남은 정책·연동·배포·운영 확인과 다음 담당을 연결한다. 코드 작성·단위 테스트·통합 검증·배포 완료는 각각 실제 수행 범위로 보고한다.

각 절은 이 폴더 내부 기준이다. 추가 기술 자료는 작업자가 제공하거나 필요할 때 선택해 참고하며, 실제 버전·코드·합의된 요구와 대조한다.
