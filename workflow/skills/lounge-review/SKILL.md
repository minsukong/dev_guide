# lounge-review — 결함·요구 충족 리뷰

## 역할과 선택 기준

명세·코드·마이그레이션이 요구를 충족하고 실제 실패 조건에서 안전하게 동작하는지 근거로 검토한다. “이 설계를 리뷰해줘”, “이번 변경의 결함을 찾아줘”, “완료 조건을 충족했는지 확인해줘” 같은 요청에 사용한다. 리뷰만 요청받은 경우 지적 결과를 제공하고 임의로 구현을 수정하지 않는다.

## 필요한 입력과 조사 범위

별도 docs/·명세가 이미 있다는 전제는 없다. 아래 참고 문서는 실제로 제공되거나 존재하는 것만 선택한다. 문서가 없으면 제공된 근거로 검토하고 미확인을 남기며, 필요할 때 프로젝트 문서를 만들어 확장할 수 있다. 없는 문서 경로·내용을 근거로 만들지 않는다.

- 필수: 검토 대상과 범위, diff 또는 설계·변경 파일, 요구·완료 조건의 근거. 기준 버전이 불명확하면 실제 비교 범위를 확인한다.
- 관련 근거: 연결된 결정·계약·기획 자료, 기존 호출자·데이터·테스트·docs/·운영 기준. [문서 연결 기준](../../development.md#project-docs)에 따라 결함 판단에 필요한 주변 범위까지 추적한다.
- 검증 자료: 실행 환경·명령·결과와 남은 제약을 확인한다. 작성자의 완료 보고와 실제 확인한 증거를 구분한다. 제공되지 않은 실행 결과를 통과로 추정하지 않는다.

## 적용과 입력

[루트 지침](../../../AGENTS.md)과 실제 백엔드 저장소 규칙을 적용한다. 입력은 검토할 설계·diff·코드와 비교 기준, 요구·완료 조건의 근거, 실제 테스트 결과다. [Workflow](../../README.md)의 관련 기준만 확인한다.

## 작업

1. 요청·카드·명세·Figma(기획서) 근거와 실제 diff·테스트 결과를 확인한다. 검토하지 못한 자료·환경을 기록한다.
2. 프로젝트 규칙 적합성과 업무 요구 충족을 각각 검토한다. 도메인 상태·권한·데이터 정합성·트랜잭션·경합·멱등성·외부 실패 중 변경에 해당하는 결함을 찾는다.
3. API 소비자·구버전 코드·기존 데이터와의 호환성, 마이그레이션·복구·관측에 필요한 항목을 확인한다. 단위 테스트 통과로 실제 DB·외부 연동 검증을 대체하지 않는다.
4. 실제 결함은 위치·발생 조건·영향·수정 방향을 근거로 제시한다. 미정 정책은 질문으로, 검토할 수 없었던 사항은 한계로 구분한다.
5. 리뷰만 요청받았다면 임의 수정하지 않는다. 필수 완료 조건과 남은 검증·담당을 연결한다. 결함이 없으면 억지로 지적하지 않는다.

산출물: 우선순위별 결함·근거 / 결정 질문 / 검증·미검증 범위 / 완료 조건 충족 여부.

## 요구와 실패 경로를 대조하는 방법

먼저 변경 목적·허용 결과·완료 조건을 정리하고 실제 diff와 연결한다. 이어서 변경된 진입점에서 권한 검사·상태 변경·저장·외부 호출·응답까지 따라간다. 정상 경로뿐 아니라 중간 실패, 동일 자원에 대한 경합, 재시도와 구버전 소비자에서 불변 조건이 유지되는지 확인한다.

테스트 개수보다 어떤 요구·실패 조건을 증명하는지 본다. 대체 객체가 항상 성공을 반환한다면 실제 DB 제약·외부 실패를 검증한 것으로 취급하지 않는다. 설계 리뷰는 실행되지 않은 설계의 위험과 필요한 검증을 제시하고, 코드 리뷰는 실제 위치·재현 조건·영향으로 결함을 설명한다.

## 결함·미정·개선 제안 구분

- 결함: 확인된 요구·계약·언어/DB 동작과 변경이 충돌하고 발생 조건·영향을 설명할 수 있는 항목이다. 실제 파일·위치와 최소 수정 방향을 남긴다.
- 미정 정책: 허용 결과 자체가 결정되지 않은 경우다. 특정 답을 가정해 결함으로 단정하지 않고 결정할 질문·담당·영향을 남긴다.
- 개선 제안: 필수 동작을 깨뜨리지는 않지만 유지보수 등을 개선할 수 있는 제안이다. 실제 결함과 분리하며 개인 스타일 선호를 필수 수정으로 제시하지 않는다.
- 검증 한계: 자료·환경 부족으로 판단할 수 없는 경우다. 확인하지 못한 대상과 필요한 증거를 적는다. 검증 한계만으로 실제 결함이 있다고 단정하지 않는다.

결함의 우선순위는 데이터 손실·권한 위반·핵심 기능 실패 등 영향과 발생 가능성·노출 범위로 설명한다. 동일 원인의 중복 지적은 묶고, 확인된 결함이 없으면 없다고 보고한다. 수정된 항목은 관련 실패 조건과 필요한 검증을 다시 확인한 뒤 잔여 사항을 갱신한다.

## 결과 형식과 사용 예시

```text
검토 범위·근거: <비교 기준 / 파일·설계·요구·테스트>
결함: <우선순위·이유 / 위치 / 발생 조건 / 영향 / 수정 방향>
결정 질문: <미정 정책·계약 / 담당 / 영향>
개선 제안: <해당할 때만, 필수 수정과 구분>
확인한 검증·한계: <직접 확인한 결과 / 미확인과 필요한 증거>
완료 조건: <충족·미충족·판단 불가 항목 / 다음 행동>
```

가상 이용권 사례: “현재 상태 조회 후 사용 이력 저장”만으로 처리하고, 동시 실행을 제어할 제약·원자적 갱신 등도 없다면 두 요청이 모두 사용 가능 상태를 읽어 중복 이력을 저장할 수 있는지 실제 코드·DB 제약을 추적한다. 성립하면 위치·실행 순서·영향을 근거로 지적한다. 반대로 제약·트랜잭션에서 보장한다면 구조가 단순해 보인다는 이유로 결함을 만들지 않는다. 예시의 실제 파일·결과는 존재하지 않으며 검토 대상에서 확인해야 한다.
