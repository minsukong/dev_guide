# lounge-implement — 백엔드 구현·검증

## 역할과 선택 기준

허용된 범위에서 기존 시스템을 수정하고 동작·검증 근거를 남기는 단계다. “이 계획대로 구현해줘”, “이 결함을 수정해줘” 같은 코드 변경 요청에 사용한다. 작은 수정은 별도 명세 없이 시작할 수 있지만 영향을 주는 규칙·계약과 완료 조건은 확인한다.

## 필요한 입력과 조사 범위

별도 docs/·명세가 이미 있다는 전제는 없다. 아래 참고 문서는 실제로 제공되거나 존재하는 것만 선택한다. 문서가 없으면 제공된 근거로 검토하고 미확인을 남기며, 필요할 때 프로젝트 문서를 만들어 확장할 수 있다. 없는 문서 경로·내용을 근거로 만들지 않는다.

- 필수: 변경할 동작·범위와 완료 조건, 실제 저장소·실행 환경, 필요한 정책·계약 근거. 큰 기능은 관련 설계·작업 기록과 남은 제약을 확인한다.
- 관련 근거: 기존 구현·호출자·테스트, docs/·API 명세·DB 변경 이력·운영 기준. [문서 연결 기준](../../development.md#project-docs)에 따라 이번 변경에 필요한 부분을 확인한다. 기획서 전체를 다시 읽는 것은 필수 절차가 아니다.
- 환경: 실제 실행 명령·설정과 테스트용 DB·연동 환경의 가용성을 확인한다. 설치·검증 명령이나 운영 접근을 추측하지 않는다.

## 적용과 입력

[루트 지침](../../../AGENTS.md)과 실제 백엔드 저장소 규칙을 적용한다. 입력은 허용된 변경 범위·완료 조건, 실제 저장소와 관련 설계·결정·정책·계약이다. [Workflow](../../README.md)의 관련 기준만 확인한다.

## 작업

1. 기존 빌드·정적검사·테스트 결과를 확인해 기준 상태와 기존 실패를 파악한다. 실제 백엔드 저장소 규칙·빌드 설정·코드·스키마·계약, 이번 범위에 필요한 정책·계약·데이터 조건과 선행 작업을 확인한다. 진행할 범위와 보류할 범위를 작업 기록에 명시한다. 확인하지 않은 스택이나 설치 명령을 가정하지 않는다.
2. 실제 소비자·테이블·배치·이벤트의 변경 영향과 API 호환성을 확인한다. 필요한 내부 개발 기준을 선택하고 도메인 규칙·상태 전이·권한을 API·데이터 처리에 반영한다. 기존 서비스·모듈·트랜잭션 경계를 따른다.
3. 변경에 해당하는 제약·동시성·멱등성·외부 호출 실패·마이그레이션 호환성을 설계·구현한다. 새 업무 정책이 필요하면 담당과 영향을 기록하고 그 부분을 분리한다.
4. 외부 시스템·소비자 계약을 대신하는 테스트 대체물은 합의된 범위에서 사용하고 가정과 한계를 명시한다. 확인된 규칙·계약에 따른 단위 테스트용 stub·fake는 개발자가 작성할 수 있으며 별도 업무 승인을 요구하지 않는다. 새 정책·외부 계약을 임의로 만들지는 않는다. 데이터 저장과 외부 처리의 성공을 임시 응답으로 숨기지 않는다.
5. 실제 저장소 명령으로 필요한 빌드·정적 검사·단위·DB/API 통합·계약/연동 테스트를 실행한다. 정상 경로와 관련 실패·중복·경합·rollback을 확인한다.
6. diff, 적용 기준, 변경 코드·스키마·계약, 검증 환경·결과, 미정·운영 전환·다음 작업을 카드에 기록한다. 필수 완료 검증이 남으면 Done으로 처리하지 않는다.

산출물: 구현 결과 / 변경 파일·계약·데이터 / 검증 근거·한계 / 인수인계. 운영 DB 변경·commit·push·배포는 실제 요청 범위에 따라 실행한다.

## 변경 위치와 구현 범위 판단

요청된 동작의 진입점에서 관련 서비스·저장·외부 호출·응답까지 따라가고, 같은 유형의 기존 코드와 테스트를 비교한다. 새 구조를 추가하기 전에 기존 책임 안에서 해결할 수 있는지 판단한다. 결함 수정에 관계없는 계층 개편이나 공통화를 덧붙이지 않는다.

정책·계약은 확인된 결과를 구현하고 기술 선택은 실제 언어·프레임워크·DB 제약에 맞춘다. 저장과 외부 호출이 함께 있으면 트랜잭션 성공과 외부 성공의 경계를 구분한다. 재시도·중복 처리·오류 응답을 임시 성공값으로 숨기지 않는다. 실제 데이터 변경·배포는 사용자가 요청한 범위와 환경을 따른다.

## 변경 유형에 맞는 검증 선택

- 업무 규칙·권한·상태 분기: 정상 결과와 허용되지 않는 행위·경계 조건을 검증한다.
- 데이터·트랜잭션·제약 변경: 실제 사용하는 DB의 동작이 중요한지 판단하고 관련 통합·rollback·경합 검증을 선택한다. 메모리 기반 대체 테스트만으로 DB 잠금·제약을 확인했다고 하지 않는다.
- API·이벤트 변경: 기존 소비자의 응답·오류·필드 호환성과 재시도·중복 전달 중 해당 조건을 검증한다.
- 마이그레이션·외부 연동 변경: 전환 순서·기존 데이터·실패·복구와 필요한 환경을 확인한다. 모든 변경에 모든 종류의 테스트를 강제하지 않는다.

## 구현 도중 충돌·실패가 발견된 경우

새 정책 결정이나 소비자 계약 변경이 필요해지면 근거·영향·담당을 기록하고 관련 부분을 보류한다. 기존 계획에 영향이 크면 설계를 갱신하며, 독립적으로 검증 가능한 범위만 계속한다. 합의된 테스트 대체물의 결과와 실제 연동 결과를 구분한다.

검증 실패는 현재 변경과의 관련성을 조사한다. 환경 미구성·기존 실패·제품 결함을 구분하고 실패를 숨기기 위해 기대값을 바꾸거나 검사를 끄지 않는다. 실행할 수 없으면 Not Run과 사유·필요 환경·다음 행동을 남긴다. 완료 조건 중 필수 검증이 남으면 구현 부분과 완료되지 않은 범위를 명시한다.

## 결과 형식과 사용 예시

```text
구현 범위·근거: <요구·결정·관련 설계>
변경 내용: <파일·동작 / API·데이터·문서 영향>
검증: <대상 / 환경 / 실제 명령 / Pass·Fail·Not Run·N/A>
진행 상태·한계: <완료 조건 충족 여부 / 미정·미검증>
인수인계: <다음 작업·담당 / 운영 전환·재개 조건>
```

가상 이용권 사례: 앞선 예시 설계와 계약이 확인된 범위에서 기존 상태 변경·이력 저장을 수정하고 정상 사용·이미 사용된 이용권·권한 없는 요청·동시 요청을 검증한다. 실제 DB 환경이 없어 경합 검증을 실행하지 못했다면 “코드 수정 및 단위 검증 완료, DB 경합 검증 Not Run”으로 남긴다. 이를 이용권 기능 전체 완료로 기록하지 않는다. 이 사례는 실제 변경·테스트 실행 결과가 아니다.
