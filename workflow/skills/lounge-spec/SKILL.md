# lounge-spec — 설계·작업 계획

## 역할과 선택 기준

확인된 요구를 기존 시스템에서 구현·검증할 수 있는 설계와 작업 계획으로 바꾼다. “어디를 어떻게 바꿀지 설계해줘”, “API와 데이터 변경 영향을 정리해줘” 같은 요청에 사용한다. 기획 검토의 질문 목록을 그대로 늘리는 대신, 확인된 규칙을 보장할 구조와 검증 방법을 정한다.

## 필요한 입력과 조사 범위

별도 docs/·명세가 이미 있다는 전제는 없다. 아래 참고 문서는 실제로 제공되거나 존재하는 것만 선택한다. 문서가 없으면 제공된 근거로 검토하고 미확인을 남기며, 필요할 때 프로젝트 문서를 만들어 확장할 수 있다. 없는 문서 경로·내용을 근거로 만들지 않는다.

- 필수: 기능 목적·포함 범위, 확인된 요구·결정 근거, 실제 백엔드 저장소 또는 관련 구조·계약 자료. 코드 접근이 없으면 개념 설계와 실제 확인이 필요한 항목을 구분한다.
- 관련 근거: Figma(기획서)·PPT의 대상 흐름, 기존 docs/·API 명세·ERD·설계 기록, 현재 코드·테스트·마이그레이션. [문서 연결 기준](../../development.md#project-docs)에 따라 이번 변경과 관련된 부분만 읽는다.
- 결과의 크기: 작은 변경은 작업 기록에 설계·검증 계획을 통합한다. 여러 작업이 공유할 규칙·계약·배포 순서가 있으면 별도 명세로 연결한다.

## 적용과 입력

[루트 지침](../../../AGENTS.md)과 실제 백엔드 저장소 규칙을 적용한다. 입력은 합의된 기능 범위·결정, 실제 저장소·계약·스키마와 관련 Figma(기획서)·PPT·기존 문서다. [Workflow](../../README.md)의 관련 기준만 확인한다.

## 작업

1. 요청·Figma(기획서)·결정 기록·기존 API/스키마에서 합의된 기능 범위와 남은 결정을 구분한다.
2. 큰 기능이면 프로젝트의 공유 설계 기록(이 폴더가 팀 기록 위치라면 tasks/SPEC-기능.md)에 목적·행위자·포함/제외, 도메인 상태·규칙·권한, API 입출력·오류, 데이터·트랜잭션, 외부 연동·호환성, 완료·검증 조건을 해당 범위에서 작성한다. 작은 작업이면 카드에 통합한다.
3. 업무 규칙의 근거와 설계 선택의 이유를 연결한다. endpoint·스키마 등은 담당 범위 안에서 제안·설계하되 새 정책과 소비자 계약은 초안/합의 상태를 구분한다.
4. 실제 호출자·공유 모듈·테이블·배치·이벤트를 따라 변경 영향을 확인한다. API 입출력·권한·오류·멱등성·소비자 호환성, 마이그레이션·배포 순서 중 관련 항목을 설계에 반영한다.
5. 검증 가능한 결과 단위로 작업을 나누고 실제 선행 조건·담당·완료 조건을 연결한다. 작업별로 검증할 결과를 명시한다.
6. 미정의 개발 영향과 담당·재개 조건을 남기고, 진행할 범위와 보류할 범위를 계획에 명시한다. 독립 검증이 가능한 부분만 분리하고 정책에 종속되는 모델·상태를 임시 값으로 확정하지 않는다.

산출물: 설계 / 작업 범위·의존성 / 검증·완료 조건 / 미정·다음 작업. 문서 작성만으로 구현·운영 변경을 시작하지 않는다.

## 설계 판단을 구체화하는 방법

호출 지점에서 권한 검사·업무 규칙·저장·응답·이벤트까지 현재 흐름을 따라가며 수정 위치를 찾는다. 기존 모듈 책임·트랜잭션·오류 처리·명명 규칙을 먼저 확인하고, 재사용 가능한 구조와 실제로 바꿔야 하는 경계를 구분한다.

대안이 필요한 경우 요구 충족, 정합성, 소비자 호환성, 운영·복구 비용을 기준으로 비교하고 선택 이유를 남긴다. 단순 변경마다 대안 문서를 만들 필요는 없다. 동시성 제어는 DB 제약·원자적 갱신·잠금 등 현재 저장소와 DB에서 가능한 방법을 검토하고, 대상 데이터·경쟁 상황·실패 결과로 적합성을 판단한다. 특정 기술을 모든 기능의 기본값으로 고정하지 않는다.

API의 입력·권한·출력·실패 의미와 기존 소비자 영향을 정리한다. 새 계약은 합의 전 초안으로 표시한다. 데이터 변경이 있으면 기존 데이터의 유효성, 구버전 코드와의 공존, 마이그레이션·배포·복구 순서 중 해당 항목을 포함한다. 외부 연동은 성공·시간 초과·중복 전달 때의 상태와 보상 책임을 확인한다.

## 작업 분할·미정과 다음 단계

파일이나 계층별로만 쪼개지 말고 검증할 수 있는 결과와 실제 의존성으로 나눈다. 각 작업에 목적·변경 위치 후보·선행 조건·완료 조건·검증을 적고 공통 계약·스키마 변경은 소비자 작업과 연결한다.

미정이 모델·상태 전이·응답을 바꾸면 그 부분은 확정 설계와 구분한다. 임시 정책·endpoint를 확정값처럼 넣지 않는다. 설계에 필요한 자료가 없으면 영향·확인할 담당과 진행 가능한 조사 범위를 남긴다. lounge-implement로 넘길 때는 승인된 범위·관련 결정·수정 위치·검증 계획·남은 제약이 이어지게 한다. 명세 작성은 코드 수정이나 배포 수행을 뜻하지 않는다.

## 결과 형식과 사용 예시

```text
목적·범위·근거: <대상 요구 / 결정·문서 링크>
현재 구조와 변경 위치: <실제 코드·모듈·계약>
설계: <업무 규칙 / API·데이터·트랜잭션 / 선택 이유>
호환성·운영 영향: <소비자·기존 데이터·배포·복구>
작업 계획: <검증 가능한 작업 / 선행 조건 / 완료 조건>
검증: <관련 정상·실패·경합 시나리오와 환경>
미정·재개 조건: <담당 / 영향 / 진행·보류 범위>
```

가상 이용권 사례: 예시 안에서만 “사용 전 상태에서 한 번만 사용 가능”이라는 정책과 중복 요청 응답 계약이 합의됐다고 가정한다. 기존 사용 처리·상태 저장·권한 검사·호출자를 조사한 뒤 동일 이용권의 동시 요청에서 하나만 상태 변경에 성공하도록 설계한다. 구현 방식은 실제 DB·코드에 맞춰 선택하고, 상태 변경과 이력 저장의 트랜잭션 경계, 중복 요청 응답, 경합 검증을 연결한다. 조사 결과 없이 특정 잠금 방식이나 endpoint를 확정하지 않는다.
