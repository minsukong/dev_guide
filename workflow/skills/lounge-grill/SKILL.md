# lounge-grill — 도메인·정책 질문 정리

## 역할과 선택 기준

기획 자료를 개발 가능한 요구와 결정 질문으로 바꾸는 단계다. “기획서를 검토해줘”, “누락된 정책을 찾아줘”, “무엇을 먼저 결정해야 하지?” 같은 요청에 사용한다. 결정할 정책을 AI가 대신 확정하는 단계는 아니다. 요구가 이미 명확하면 설계나 구현 단계부터 시작할 수 있다.

## 필요한 입력과 조사 범위

별도 docs/·명세가 이미 있다는 전제는 없다. 아래 참고 문서는 실제로 제공되거나 존재하는 것만 선택한다. 문서가 없으면 제공된 근거로 검토하고 미확인을 남기며, 필요할 때 프로젝트 문서를 만들어 확장할 수 있다. 없는 문서 경로·내용을 근거로 만들지 않는다.

- 필수: 대상 기능·검토 목적, 읽을 수 있는 기획 자료 또는 현재 문제 설명. 자료가 없으면 확인 가능한 사실과 추가로 필요한 자료를 먼저 정리한다.
- 관련 근거: Figma(기획서)·PPT, 기존 docs/·정책·API 명세, 이전 결정·코멘트, 필요할 때 현재 코드·테스트. [프로젝트 문서 연결 기준](../../development.md#project-docs)에 따라 관련 부분만 읽는다.
- 범위: 행위자, 시작 조건, 정상·실패·종료 흐름과 관련 전후 기능을 확인한다. 파일·버전·노드 또는 슬라이드를 근거로 남긴다. 자료를 읽지 못한 상태를 기획 누락으로 단정하지 않는다.

## 적용과 입력

[루트 지침](../../../AGENTS.md)과 실제 백엔드 저장소 규칙을 적용한다. 입력은 대상 기능·검토 목적, Figma(기획서)·PPT·기존 문서 등 실제로 제공된 근거다. [Workflow](../../README.md)의 관련 기준만 확인한다.

## 작업

PPT 기획서는 [PPT 읽기·검토 기준](../../development.md#ppt-input)에 따라 파일·버전·슬라이드, 텍스트·이미지·노트의 확인 범위를 남긴다. 아래 Figma(기획서) 연결 확인은 Figma 자료에만 적용한다.

1. Figma(기획서)를 직접 읽는 경우 MCP/API 연결 방식과 대상 화면 하나의 실제 읽기를 먼저 확인한다. 오류·부분 응답은 내부 접근 기준에 따라 처리한다. 이후 관련 화면·주석·기존 정책·현재 백엔드 동작을 확인하고 출처·노드·날짜·관찰 범위를 기록한다.
2. Figma(기획서) 링크를 받은 경우 화면인지 메뉴 전체인지와 요청 목적을 확인한다. 큰 메뉴는 구조·목록을 먼저 파악하고 화면 묶음별로 상세 검토한다. 읽은 노드·정책·미정·미확인 범위를 기록해 컨텍스트를 관리하고, 전체 검토 요청은 묶음별 확인 후 범위 전체를 대조한다.
3. 행위자·권한, 업무 상태·전환 조건, 데이터 소유권·유효 기간, 취소·중복·재시도에서 서버가 보장할 동작을 찾는다. 화면 필드를 곧바로 스키마로 변환하지 않는다.
4. 확인됨 / 검토 범위에서 미확인 / 충돌 / 접근 불가를 구분한다. 관련 근거에 이미 답이 있으면 연결하고 반복 질문하지 않는다.
5. 업무 정책의 결정, 소비자·연동 담당과 합의할 계약, 개발자 책임의 기술 설계를 구분한다. 상태 전이·권한·정합성을 바꾸는 질문부터 우선한다.
6. 질문에는 실제 상황·결정 담당·영향받는 API/데이터/테스트·재개 조건·독립 진행 범위를 남긴다. 예를 들어 동시 사용 요청의 허용 결과는 정책 질문이고, 그 결과를 보장할 제약·잠금 방식은 기술 설계다.

7. 기획서 보완이 필요하면 공통 코멘트 양식으로 현재 확인·질문·기획서 반영 요청·개발 영향·협의 대상을 작성한다. 기존 코멘트와 결정에서 중복을 확인하고, 관련된 하나의 결정 주제 단위로 묶는다.
8. 요청이 초안인지 게시까지인지 구분한다. 게시 요청이면 대상·범위, 코멘트 게시 도구·계정 권한을 확인해 수행하고 실제 코멘트 ID·링크를 남긴다. 게시가 불가능하면 초안과 필요한 설정을 반환한다. 게시 요청이 명확한데 매번 별도 승인 단계를 강제하지 않는다.
9. 답변을 받으면 결정자·적용 범위를 결정 기록에 연결하고 작업 범위·재개 조건·기획서 반영 상태를 갱신한다. 코멘트 작성과 정책 확정·구현 완료를 구분한다.

산출물: 확인한 요구 / 우선 질문·담당 / 개발 영향 / 진행 범위 / 코멘트 초안 또는 실제 게시 결과. 새 질문은 결정 기록과 관련 작업에 연결한다. AI 제안만으로 정책을 확정하지 않는다.

## 질문을 만드는 판단 기준

먼저 “누가 어떤 조건에서 어떤 상태를 바꾸며 무엇을 보장해야 하는가”를 정리한다. 그다음 실패·취소·만료·중복·재시도가 기존 규칙으로 설명되는지 대조한다. 모든 기능에 같은 질문 목록을 적용하지 않고 이번 흐름에 영향을 주는 항목만 다룬다.

- 정책 질문: 이용권 사용 후 취소 허용 여부, 사용 가능한 주체와 시간처럼 허용 결과를 결정하는 문제다. 결정할 역할과 필요한 선택지를 제시한다.
- 계약 협의: 이미 처리한 요청의 응답·오류 의미, 프론트·외부 시스템과 공유할 상태처럼 소비자와 합의할 문제다. 영향을 받는 호출자를 확인한다.
- 기술 설계: 합의된 결과를 보장하기 위한 제약·잠금·트랜잭션 방식이다. 설계 단계에서 판단하며, 기획 담당에게 구현 방식 선택을 떠넘기지 않는다.

질문은 상태·권한·정합성·소비자 계약에 미치는 영향과 선행 관계로 우선순위를 정한다. “정책이 부족합니다” 대신 실제 발생 상황, 현재 근거, 결정할 내용, 개발 영향과 독립적으로 진행할 범위를 적는다.

## 자료 부족·충돌 처리와 다음 단계

문서와 코드가 다르면 문서가 목표 상태인지, 코드가 현행 동작인지부터 구분한다. 최신 승인본·담당이 확인되지 않으면 차이와 영향만 기록하고 한쪽을 자동 정답으로 정하지 않는다. 접근 불가 자료는 필요한 파일·권한과 미확인 범위를 남긴다.

전체 기능이 미정이라고 일괄 보류하지 않는다. 핵심 정책에 종속된 모델·상태 변경은 보류하되 근거 조사·영향 분석 등 독립 작업은 진행할 수 있다. 설계에 필요한 결정이 확인되면 관련 결정 ID와 남은 질문·제약을 lounge-spec에 전달한다. 코멘트 절차는 Figma(기획서)에 게시를 요청받은 경우 해당 도구·양식을 적용한다. PPT 검토 요청을 댓글 작성 요청으로 확대하지 않는다.

## 결과 형식과 사용 예시

```text
검토 범위·근거: <파일·버전·노드/슬라이드·관련 docs>
확인된 요구: <근거와 적용 범위>
질문: <실제 상황 / 결정할 내용 / 담당 / 관련 DEC>
개발 영향: <API·상태·데이터·테스트 영향>
진행 가능 / 보류·재개 조건: <각 범위와 필요한 결정>
미확인: <자료·접근 제한과 필요한 조치>
```

가상 이용권 사례: 기획에는 사용 버튼과 완료 화면만 있고 중복 요청의 결과가 설명돼 있지 않다. 기존 정책·API 명세에도 답이 없다면 “동일 이용권 사용 요청이 겹칠 때 업무상 허용 결과는 무엇이며, 재시도 시 어떤 결과를 안내해야 하나요?”를 묻는다. 정책·계약 확인 전 해당 상태 변경과 응답을 확정하지 않고, 현재 처리 흐름 조사와 경쟁 조건 분석은 진행할 수 있다고 구분한다. 실제 서비스 정책이나 검토 결과가 아니다.
