# 정책·계약 결정 기록

이 파일은 배포용 양식이며 현재 등록된 실제 결정은 없다. 실제 기록은 [프로젝트의 공유 결정 기록 위치](README.md#shared-records)에 남기고, 개인 가이드 복사본마다 확정 결정을 따로 관리하지 않는다. 팀이 이 파일을 공유 원본으로 정했다면 여기서 관리할 수 있다. 기획·계약의 미정과 충돌이 생기면 아래 항목으로 기록한다. 설계 초안과 확정 정책을 구분한다.

```text
ID / 상태: 미정·제안·확정·대체됨
근거: Figma(기획서) URL·노드·확인 날짜 / 정책·API·현재 코드
확인한 내용·관찰 범위 / 결정할 질문:
결정 담당 / 협의할 소비자·연동 담당:
개발 영향·관련 작업 / 진행할 범위 / 재개 조건:
결정 내용·결정자·일자·근거·적용 범위:
대체된 결정: 해당할 때
```

예시로, 이용권의 동시 사용·재시도 규칙이 미정이면 허용 상태 전이와 중복 요청의 결과를 담당과 확인한다. 변경 API·데이터 제약·트랜잭션·경합 테스트에 미치는 영향을 연결한다. 정책 확인 전에는 코드 조사와 설계 대안을 검토할 수 있지만, 정책에 종속되는 저장 모델·변경 동작을 확정 사양으로 반영하지 않는다. 이 예시는 실제 이용권 정책이 아니다.

## Figma(기획서) 보완 코멘트 — 사람·AI 공통 양식

화면 설명이 부족하거나 서로 충돌할 때 대상 화면에 아래 양식으로 코멘트를 남긴다. 관련 화면·설명·결정·기존 코멘트에 이미 답이 있는지 먼저 확인한다. 한 코멘트에는 함께 결정해야 할 한 가지 주제를 담는다. 긴 내부 설계 검토는 작업 기록으로 연결한다.

```text
[기획 보완 요청] <기능> — <결정할 항목>
대상: <화면명·노드 링크>
현재 확인: <관련 화면·설명에서 확인한 내용>
확인 요청: <실제 상황과 결정할 질문>
기획서 반영 요청: <추가할 정책·조건·분기·상태 설명>
개발 영향: <영향받는 API·데이터·테스트, 진행·보류 범위>
협의 대상: <결정할 역할·담당자, 모르면 확인 필요>
```

‘기획서 반영 요청’에는 결정된 내용을 어느 흐름·상태·설명에 추가할지 쓴다. ‘상세 기획 부탁드립니다’처럼 범위가 불분명한 요청을 피한다. 실제 담당·기한은 확인된 경우에만 지정하고, 선택지·기술 제안은 확정 정책과 구분한다. 기존 결정 ID가 있으면 제목이나 본문에 연결한다.

<a id="comment-example"></a>
## 적용 예시 — 실제 검토 결과·정책이 아님

```text
[기획 보완 요청] 이용권 사용 — 중복 요청 처리
대상: 이용권 사용 화면 / <실제 화면·노드 링크>
현재 확인: 사용 동작은 있지만, 검토한 화면·설명에서 중복 처리 기준을 찾지 못했습니다.
확인 요청: 같은 이용권의 사용 요청이 동시에 오거나 처리 후 재시도될 때 각각 어떤 결과를 반환해야 하나요?
기획서 반영 요청: 허용 결과, 오류·안내, 재시도 기준을 사용 흐름 설명에 추가해 주세요.
개발 영향: 변경 API·데이터 제약·트랜잭션·테스트에 영향을 줍니다. 해당 동작의 구현은 결정 후 진행하고, 기존 코드 조사와 설계 대안 검토는 진행할 수 있습니다.
협의 대상: 기획·운영 정책 담당과 백엔드 협의 필요 / 실제 담당 확인 필요
```

## 직접 작성과 AI 요청

- 사람이 직접 남길 때: 대상 화면에서 코멘트 기능을 선택해 관련 위치에 핀을 두고 양식을 작성한다. 기존 스레드에서 같은 질문을 논의 중이면 새 코멘트 대신 해당 스레드에 이어서 남긴다.
- AI에게 초안을 요청할 때: 기획서 링크·검토 범위를 제공하고 이 양식으로 작성하게 한다. 초안 작성만 요청했다면 게시하지 않는다.
- AI에게 게시를 요청할 때: 대상과 게시 범위를 확인하고, 실제 도구의 코멘트 게시 기능과 계정 권한을 확인해 게시한다. 대상·범위가 명확하게 요청됐다면 매번 별도 승인 단계를 추가하지 않는다. 위치 고정이 지원되면 대상 노드·영역에 연결하고, 지원되지 않으면 본문에 확인된 대상 링크를 넣는다.
- 게시 성공은 반환된 코멘트 ID·링크 등 실제 결과로 확인한다. 게시 도구·권한이 없으면 초안과 필요한 설정을 제공하고 사람이 등록하도록 안내한다. 실제 실패를 게시 완료로 보고하지 않는다.

REST API를 사용하면 기존 코멘트 조회는 file_comments:read, 게시는 file_comments:write가 필요하다. file_content:read만으로 코멘트 게시 권한이 생기지 않는다. 실제 파일·계정 권한과 사용하는 도구의 지원도 확인한다. 공식 MCP 연결·캔버스 편집 지원만으로 코멘트 게시 기능을 가정하지 않는다. [공식 Comments API](https://developers.figma.com/docs/rest-api/comments-endpoints/) · [Scope 기준](https://developers.figma.com/docs/rest-api/scopes/) (2026-10-28 확인).

### AI에게 초안 요청

```text
Figma(기획서): <대상 화면·노드 링크>
검토 범위: <기능·흐름>
lounge-grill과 공통 코멘트 양식을 사용해 기획 보완 코멘트 초안을 작성해줘.
관련 화면·설명·기존 결정·코멘트에서 먼저 답을 찾고 중복 질문은 제외해줘.
결정할 질문, 기획서 반영 요청, 개발 영향·담당을 포함해줘. 아직 게시하지 마.
```

### AI에게 게시 요청

```text
Figma(기획서): <대상 화면·노드 링크>
게시할 내용: <게시할 코멘트 본문 또는 이번에 검토할 범위>
공통 양식으로 기획 보완 코멘트를 작성해 해당 화면에 게시해줘.
기존 코멘트와 중복을 확인하고, 게시 결과와 코멘트 링크 또는 ID를 남겨줘.
게시 도구·권한이 없으면 초안과 필요한 설정을 알려줘. 게시한 것으로 처리하지 마.
```

<a id="comment-followup"></a>
## 답변 이후 기록

게시했다면 해당 결정 항목에 대상 화면과 코멘트 링크 또는 ID를 연결한다. 초안이면 ‘초안·미게시’, 사람이 등록했다면 실제 등록 결과를 기록한다.

답변이 오면 결정자·내용·근거·적용 범위를 위 결정 항목에 반영하고 관련 작업의 진행·보류 범위와 재개 조건을 갱신한다. 기획서에 반영됐는지도 확인하고 아직 미반영이면 구분해 남긴다. 질문을 게시했다는 사실이나 담당이 확인되지 않은 답변만으로 정책 확정·개발 완료로 처리하지 않는다. 기존 코멘트를 임의로 삭제·해결 처리하지 않는다.
