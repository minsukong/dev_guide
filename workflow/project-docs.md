# 권장 확장 — 프로젝트 docs로 지식 쌓고 운영하기

이 가이드로 실제 작업을 시작한 뒤, 기능과 참여자가 늘어나면 프로젝트 문서를 함께 운영하는 방식을 권장한다. 작업마다 같은 정책·코드 구조·실행 방법을 다시 설명하지 않고, 개발자와 AI가 필요한 근거를 찾아 이어서 작업할 수 있게 하는 것이 목적이다. 프론트엔드에서 공통 가이드와 프로젝트 지식을 연결해 운영하는 방식처럼, 백엔드도 자기 도메인과 저장소에 맞게 확장할 수 있다.

<a id="roles"></a>
## 공용 가이드·프로젝트 docs·작업 기록의 역할

| 구분 | 담을 내용 | 관리 방식 |
| --- | --- | --- |
| 공용 dev_guide | 기획 검토·설계·구현·검증·리뷰의 공통 방법 | 공용 원본에서 관리하고 여러 프로젝트가 참조 |
| 프로젝트 docs | 그 프로젝트의 업무 규칙·API 계약·데이터 설계·실행 방법 | 해당 개발팀이 실제 소스·기획·결정 근거와 연결해 관리 |
| 결정·작업 기록 | 무엇을 왜 결정했는지, 이번에 무엇을 바꾸고 검증했는지 | 팀의 공유 위치에서 이력·상태·담당을 관리 |

프로젝트 docs는 반복해서 쓸 내용을 찾기 쉽게 정리한 현재 기준이고, 결정·작업 기록은 그 기준이 만들어지거나 바뀐 근거다. 같은 정책의 확정본을 여러 곳에서 따로 수정하지 않는다. 기존 API 명세·공유 문서가 있다면 기준 위치를 유지하고 docs에서는 필요한 설명과 링크를 연결한다. [공유 기록 기준](README.md#shared-records)을 따른다.

<a id="start-small"></a>
## 언제부터 무엇을 정리하면 좋은가

처음에는 제공된 기획 자료·소스와 작업·결정 기록으로 시작한다. 같은 내용을 다시 설명하게 되거나 다른 개발자가 합류하고 AI 작업을 이어가야 한다면, 자주 찾는 내용부터 프로젝트 docs로 정리한다.

| 반복되는 상황 | 먼저 정리할 문서 | 다음 작업에서 얻는 점 |
| --- | --- | --- |
| 저장소 구조·실행 방법을 매번 설명함 | 문서 목차, 모듈 위치, 개발·테스트 실행 방법 | 새 작업의 준비 시간을 줄임 |
| 취소·만료·권한 규칙을 여러 기능에서 사용함 | 도메인 규칙·상태 전이와 관련 결정 | 기능별로 서로 다른 정책을 구현하는 일을 줄임 |
| FO·BO·외부 연동 담당이 같은 API를 참조함 | API 계약의 기준 위치, 오류·인증·호환성 설명 | 같은 입출력·실패 의미로 구현하고 검증 |
| 테이블·이벤트 변경이 다른 작업에 영향을 줌 | 데이터 소유·제약·트랜잭션·이행 순서 | 공유 데이터와 배포 순서의 영향을 추적 |
| 담당자가 바뀌거나 장애 대응을 인계함 | 환경별 실행·관측·재처리·복구 절차 | 검증된 절차와 남은 운영 확인을 구분 |

한 번의 작은 수정마다 별도 문서를 만들 필요는 없다. 반복해서 쓰는 규칙·계약·실행 방법을 작업 기록에서 골라 정리한다. 프로젝트 docs를 운영한다고 새 스킬까지 반드시 만들어야 하는 것은 아니다. 기존 네 스킬에 프로젝트 문서의 위치를 연결하는 것으로 시작할 수 있다.

<a id="structure"></a>
## 추천 구조 예시

아래는 확장 방향을 보여주는 예시이며 현재 백엔드에 이 경로가 있다는 뜻은 아니다. 필요한 파일부터 만들고 기존 저장소 구조와 공유 명세 위치를 재사용한다. docs/는 권장 위치의 예시다.

```text
backend-repository/
├── AGENTS.md                 기존 지침에 문서 진입점과 선택 기준 연결
└── docs/
    ├── README.md             문서 목차·기준 위치·담당·상태
    ├── domain/               업무 규칙·권한·상태 전이
    ├── api/                  API 계약 설명 또는 기존 명세로 연결
    ├── data/                 데이터 소유·제약·트랜잭션·변경 순서
    └── operations/           로컬 실행·테스트·배포·복구 방법

결정·작업 기록은 이미 정한 팀 공유 위치를 연결한다.
```

docs/README.md에는 어떤 작업에서 어느 문서를 읽어야 하는지 짧게 적는다. 예를 들어 이용권 취소 변경은 취소 정책·해당 API 계약·데이터 상태 전이만, 테스트 환경 수정은 실행·테스트 안내만 연결한다. AGENTS.md에는 이 진입점과 선택 기준을 연결하고 문서 본문 전체를 복제하지 않는다.

<a id="cycle"></a>
## AI 작업과 문서 갱신을 연결하는 흐름

1. **작업 시작:** 공용 가이드와 프로젝트 문서 목차에서 이번 기능의 정책·계약·관련 코드·실행 방법을 찾는다. 필요한 부분과 원문 근거를 읽고 현재 코드·설정과 대조한다.
2. **설계·구현:** 확인된 규칙과 공유 결정에 따라 작업한다. 새로운 정책 질문이나 계약 변경은 제안·미정으로 기록하고 영향받는 범위를 구분한다.
3. **검증·리뷰:** 요구 충족, 실제 변경과 테스트 결과, 문서에 적힌 동작·명령의 일치 여부를 확인한다. 문서 작성과 동작 검증은 별개의 결과로 남긴다.
4. **문서 갱신:** 업무 규칙·API·데이터·실행 방법이 바뀌었다면 관련 문서도 같은 변경 흐름에서 갱신하고 결정·작업·코드 기준점을 연결한다. 갱신이 남았다면 해당 범위·담당·사유를 기록한다.
5. **다음 작업:** 새 대화나 다른 개발자도 공유 문서 목차·결정·작업 링크에서 재개한다. 대화에만 남은 결론을 팀의 기준으로 사용하지 않는다.

문서별로 적용 기능·기준 버전 또는 확인일·근거·상태·관리 담당을 필요한 범위에서 남긴다. 합의된 목표 동작, 현재 코드에서 확인한 동작, 제안·미정을 구분한다. 기획·문서·코드가 다르면 목표와 현행의 차이부터 확인하고 담당에게 연결한다. 코드가 다르다는 이유로 승인된 정책 문서를 코드에 맞춰 임의로 바꾸지 않는다.

예를 들어 취소 허용 조건이 확정되면 도메인 문서에서 조건·상태 전이와 결정 근거를 정리하고 API 계약의 응답·오류 의미를 연결한다. 구현에서 상태 변경·트랜잭션을 반영하고 테스트로 확인한 뒤 관련 코드·검증 결과를 작업 기록에 남긴다. 이후 취소 조건이 바뀌면 같은 문서·계약·테스트의 영향을 함께 확인한다. 이 예시는 실제 취소 정책이나 API 사양을 정의하지 않는다.

<a id="ai-request"></a>
## AI에게 문서 확장을 요청하는 방법

처음 정리할 때는 읽기·문서 정리 범위를 지정한다. 기존 문서가 있으면 새 구조를 먼저 만드는 대신 내용을 찾아 연결하도록 한다.

```text
공용 가이드: <dev_guide 경로>
프로젝트 저장소: <실제 백엔드 경로>
기준 자료·공유 기록: <기획서·결정·작업·API 명세의 위치>
정리할 범위: <예: 확정된 취소 규칙과 관련 코드·테스트 실행 방법>

가이드와 저장소 지침을 읽고, 기존 문서·소스·결정을 확인해줘.
반복해서 참조할 내용을 프로젝트 docs로 정리하고 문서 목차에 연결해줘.
기존 명세가 있으면 기준 위치를 유지하고 필요한 설명과 링크를 추가해줘.
확정·현행 코드 동작·제안·미정을 구분하고 근거·담당·적용 범위를 남겨줘.
예시 폴더를 전부 만들지 말고 이번 범위에 필요한 문서만 작성해줘.
이번 요청은 문서 정리까지야. 애플리케이션 코드는 수정하지 마.
```

문서가 생긴 뒤의 구현 요청에는 문서 진입점과 관련 범위를 함께 전달한다.

```text
공용 가이드: <dev_guide 경로>
프로젝트 저장소·문서 진입점: <실제 소스와 docs 목차 경로>
작업·결정: <공유 링크 / 이번 범위와 완료 조건>

이번 작업에 필요한 정책·계약·실행 안내와 실제 코드를 확인해줘.
관련 스킬을 적용해 구현·검증하고, 동작·계약·실행 방법이 바뀌면
요청 범위 안에서 관련 프로젝트 문서도 갱신해줘.
변경 코드·문서·실제 검증 결과와 남은 결정·갱신 항목을 함께 남겨줘.
```

문서를 정리했다고 정책 승인·실제 연동·배포가 완료되는 것은 아니다. 실제 수행한 결과와 다음 담당을 [작업 양식](task-template.md)의 항목에 맞춰 공유 기록에 남긴다.
