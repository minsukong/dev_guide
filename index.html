백엔드 AI 개발 가이드

개발자와 AI가 요구 확인부터 설계·구현·테스트·리뷰까지 함께하는 공통 개발 프로세스

1. 개발자와 AI가 함께하는 개발 프로세스

이 가이드는 개발자와 AI가 요구 확인·설계·구현·테스트·리뷰를 함께 진행하는 공통 개발 프로세스를 설명합니다. 개발자가 목표·범위와 필요한 결정을 맡고, AI가 자료·코드 조사, 설계안, 구현과 검증을 지원합니다.

기획 자료·현재 코드·공유 결정을 함께 확인하고 실제 검사 결과를 보며 작업합니다. 변경한 기능을 테스트하고 실패 원인을 AI와 수정·재검증한 뒤, 개발자가 중요한 판단과 남은 검증을 확인해 다음 작업으로 연결합니다.

테스트 결과를 기준으로 협업하기

반복 확인은 프로젝트의 공통 빌드·정적검사·테스트로 묶고, 개발자와 AI가 같은 명령과 결과를 기준으로 작업합니다. 공통 검사 구성과 실행 환경은 백엔드 팀이 개발표준과 실제 저장소에 맞춰 관리합니다.

  1. 시작할 때: 기존 검사 결과를 확인해 현재 상태와 이미 있던 실패를 파악합니다.
  2. 변경할 때: AI가 구현과 관련 테스트를 함께 작성·수정하고 필요한 검사를 실행합니다.
  3. 검사 후: 실패 결과를 AI와 확인해 수정·재실행하고, 개발자는 중요한 업무 판단과 자동화하지 못한 범위를 확인합니다.
  4. 완료할 때: 실제 실행 결과와 남은 검증을 리뷰·인수인계에 연결합니다. AI의 완료 보고만으로 통과한 것으로 보지 않습니다.

PPT로 기획서를 전달받은 경우

PPT(.ppt·.pptx)도 AI와 함께 검토할 수 있습니다. 파일을 첨부하거나 AI가 읽을 수 있는 파일 경로·공유 링크를 전달하고, 파일명·버전, 검토할 기능, 슬라이드 번호·제목을 지정합니다. 여러 파일이 있으면 최신 승인본과 참고본부터 구분합니다. PPT를 읽는 데 Figma(기획서) 연결이나 API 토큰이 필요한 것은 아닙니다.

  1. 범위 지정: 목차와 전체 흐름을 먼저 파악하고 대상 기능·전후 흐름을 나눠 읽습니다. 긴 파일은 기능별로 검토하며 근거·결정·미정을 기록해 컨텍스트를 관리합니다.
  2. 내용 확인: 본문·표·발표자 노트와 화면 이미지·도형·화살표를 함께 확인합니다. 텍스트만 추출됐다면 화면 배치나 상태 분기까지 읽었다고 보지 않습니다.
  3. 요구사항 도출: 업무 규칙·상태·데이터·권한·API·오류·재시도·취소 조건을 검토합니다. 확인된 요구, 기존 자료에서 답을 찾지 못한 질문, 읽지 못한 범위를 구분합니다.
  4. 결과 연결: 파일·버전·슬라이드를 근거로 남기고, 미정의 담당·개발 영향·재개 조건을 결정 기록과 작업에 연결합니다. 화면만으로 API·DB 설계를 확정하지 않습니다.

PPT 파일을 열었다고 기획서 전체를 읽은 것은 아닙니다. 이미지 안의 글자·화면 연결·발표자 노트는 도구에 따라 누락될 수 있습니다. .ppt를 읽지 못하면 원본을 보존하고 .pptx 또는 PDF 사본으로 검토합니다. PDF·캡처로 대체한 경우 원본에서 확인하지 못한 정보는 미확인으로 남깁니다.

AI 도구·MCP·스킬의 역할

개발자는 AI 도구에 작업을 요청합니다. AI 도구는 스킬의 지침을 적용하고, 연결된 도구로 자료를 읽거나 코드를 수정·검증합니다.

스킬 파일이나 기획서 URL을 전달하는 것과 실제 자료에 접근할 도구·권한을 준비하는 것은 별도입니다. 기획서를 읽는 연결은 다음 순서로 확인합니다.

화면 하나를 지정할지, 메뉴 전체를 전달할지 정합니다

Figma(기획서)에는 화면 설계·설명·상태·화면 간 이동 흐름이 함께 있습니다. 페이지는 자료를 묶는 영역, 프레임은 보통 한 화면이나 화면 묶음, 노드는 프레임·텍스트 등 개별 요소를 가리킵니다. 프로토타입은 화면 사이의 이동·상호작용을 확인하는 기능입니다.

본인 계정으로 기획서를 열어 자료를 볼 수 있는지 확인한 뒤, 작업 목적에 맞게 링크를 전달합니다. 여기서 메뉴 전체는 ‘회원’·‘이용권’처럼 한 기능 영역의 화면·상태·흐름을 묶은 범위를 뜻합니다. 페이지·섹션·파일 링크를 주더라도 어느 메뉴와 기능을 검토할지 함께 적습니다.

전달 방식장점·적합한 작업단점·보완 방법
화면·프레임 선택 링크
해당 화면을 선택해 그 대상의 링크를 복사하고, 작업할 동작을 지정		읽을 범위가 명확해 빠르게 확인하기 좋습니다. 상세 설계·특정 API 요구 확인·작은 변경에 적합하고, 불필요한 도구 조회와 AI 입력을 줄이기 쉽습니다.진입 조건·이전/다음 화면·공통 정책이 빠질 수 있습니다. 관련 흐름·설명이 있으면 링크를 추가하거나 AI가 필요한 화면을 찾아 확인하도록 범위를 지정합니다.
메뉴·기능 전체 링크
화면 묶음이 있는 페이지·섹션·파일 링크와 메뉴·검토 목적을 함께 전달		처음 기능을 파악하거나 화면 사이 정책·분기·누락을 비교하기 좋습니다. 큰 기능의 설계와 작업 분해에 필요한 전체 흐름을 확인할 수 있습니다.상세 자료를 모두 읽으면 조회·이미지·텍스트 입력이 늘어 시간·AI 토큰·사용량 부담이 커질 수 있습니다. 자료가 많으면 컨텍스트도 과밀해집니다. 먼저 구조를 파악하고 필요한 화면 묶음을 순차로 읽습니다.

주의메뉴 전체 링크는 ‘전체 내용을 한 번에 읽기’ 요청과 다릅니다

링크 주소 자체보다 그 링크에서 실제로 가져오는 화면·텍스트·이미지와 반복 조회가 비용과 시간에 영향을 줍니다. 링크를 받았다고 하위 화면을 전부 읽은 것도 아닙니다. 실제 도구의 접근 범위와 읽은 노드를 확인합니다.

Figma(기획서)의 API·MCP 호출 한도, AI 제공자의 토큰·사용량 한도, 한 번에 참고할 수 있는 컨텍스트 한도는 서로 다른 제한입니다. 어느 한도를 만났는지 구분해야 합니다.

컨텍스트: AI가 현재 작업에서 참고하는 정보 범위

컨텍스트는 AI가 현재 답변·판단을 만들 때 함께 참고하는 작업 공간입니다. 대화, 지침·스킬, 읽은 코드, 기획서 텍스트·이미지, 도구 응답이 여기에 포함됩니다. 토큰은 모델이 이런 입력·출력을 처리할 때 사용하는 단위입니다.

메뉴의 상세 자료를 한꺼번에 넣으면 핵심 정책·현재 작업과 무관한 내용이 섞이고, 앞서 확인한 조건을 놓치거나 결과가 일부 누락될 수 있습니다. 한도에 가까워지면 도구·모델에 따라 입력·응답이 잘리거나 이전 내용이 요약·제외될 수 있으므로, 한 번 읽은 내용을 이후에도 모두 그대로 참고한다고 가정하지 않습니다. 정확한 한도와 처리 방식은 사용하는 도구·모델에 따라 다릅니다.

메뉴 전체를 검토할 때

대상: <메뉴·페이지·섹션 또는 파일 링크> 범위: <예: 이용권 메뉴의 조회·사용·취소 흐름> 먼저 페이지·화면 목록과 연결 관계를 파악하고, 필요한 화면 묶음으로 나눠줘. 전체 원문을 한 번에 가져오지 말고 <우선 검토할 기능>부터 상세히 읽어줘. 전체 검토가 필요하면 묶음별로 순차 확인하고 결과를 기록해줘. 각 묶음의 노드 링크·확인한 정책·미정 질문·미확인 범위를 남겨줘.

권장 순서: 메뉴 구조·화면 목록 확인 → 현재 작업과 관련된 화면 묶음 상세 확인 → 근거 링크·정책·미정 기록 → 다음 묶음 확인. 전체 메뉴 검토가 목적이면 같은 방식으로 범위를 끝까지 확인하고, 마지막에 화면 간 정책·흐름을 대조합니다. 구조만 확인한 상태와 상세 검토 완료를 구분합니다.

REST API 직접 조회도구·스크립트에서 인증과 필요한 읽기 scope 설정파일 접근권한, endpoint·좌석·파일이 속한 플랜에 따른 호출 제한

MCP 서버 주소는 AI 도구의 연결 설정에 넣고, 기획서 화면 링크는 작업 요청에 전달합니다. 좌석(seat)은 계정에 배정된 이용 유형입니다. 파일 열람권한과 필요한 좌석·플랜을 각각 확인합니다.

주의기획서 조회는 권한·호출 제한으로 중단될 수 있습니다

REST API로 Figma(기획서)의 파일·노드를 읽을 때는 다음 조건을 먼저 확인합니다.

  • 권한 오류·403: 연결 계정의 파일 접근권한과 인증 범위(scope)를 확인합니다.
  • 호출 제한·429: 요청 한도에 도달하면 조회가 중단됩니다. 오류 경로와 Retry-After를 확인하고 실패한 요청을 반복하지 않습니다.
  • 유료 계정도 파일이 속한 플랜의 영향을 받습니다. 계정 좌석과 대상 파일의 플랜을 함께 확인합니다.
  • MCP에도 읽기 도구 한도가 있습니다. 실제로 사용 중인 연결이 MCP인지 REST API인지 확인합니다.

다음 조치: 권한·한도 문제를 확인한 뒤 재시도하고, 응답이 큰 경우에는 파일 전체 대신 필요한 화면·노드로 범위를 줄입니다.

이 절의 API는 개발 중인 서비스 API가 아니라 Figma(기획서) 데이터 조회 API를 뜻합니다.

REST API를 쓴다면 토큰을 실행 도구에 설정합니다

AI가 REST API를 호출하려면 그 요청을 실행하는 도구에 인증정보가 제공돼야 합니다. 공식 Remote MCP는 계정 로그인과 접근 허용으로 인증을 연결하므로 일반적인 설정에서 개인 토큰을 따로 발급해 전달하지 않습니다. 직접 REST API를 호출하거나 개인 토큰을 요구하는 연동 도구를 사용하는 경우에는 해당 도구에 토큰을 설정합니다.

  1. 개인 스크립트·로컬 도구에 쓸 토큰이 필요하면 Figma(기획서) 계정의 Settings → Security → Personal access tokens → Generate new token에서 만료 기간과 필요한 읽기 scope를 정합니다. 파일 본문 읽기는 file_content:read를 사용하고, 추가 자료는 해당 도구가 요구하는 범위를 확인합니다.
  2. 발급된 값은 사용하는 AI·연동 도구의 인증 설정이나 실행 환경의 비밀값으로 등록합니다. 환경변수 이름은 도구마다 다릅니다. FIGMA_ACCESS_TOKEN은 직접 작성한 스크립트에서 사용할 수 있는 예시 이름이며, 변수만 만들면 모든 도구가 자동 인식하는 것은 아닙니다.
  3. AI에는 토큰 값 대신 설정 위치·변수명·사용 방식을 전달합니다. AI가 실행하는 도구 프로세스에서도 그 설정을 읽을 수 있어야 합니다. 개인 토큰을 직접 REST 요청에 쓸 때는 X-Figma-Token 헤더에 넣습니다.
  4. 대상 화면 하나로 읽기를 확인합니다. 토큰 발급만으로 파일 접근권한이나 호출 한도가 늘어나지는 않으므로 403·429는 아래 항목을 확인합니다.

만든 문서를 계속 사용하는 방법

  1. 시작: 저장소의 AGENTS.md와 문서 목차에서 이번 기능에 필요한 정책·계약·실행 안내를 찾고 실제 코드와 대조합니다.
  2. 작업: 관련 스킬로 설계·구현·검증합니다. 새 정책 질문과 계약 변경은 결정·작업 기록에 연결합니다.
  3. 갱신: 동작·계약·실행 방법이 바뀌면 관련 문서도 같은 변경 흐름에서 갱신하고 근거·담당·기준 코드·검증 결과를 남깁니다.
  4. 재사용: 다른 개발자나 새 AI 대화는 문서 목차와 관련 결정·작업 링크에서 이어갑니다.

합의된 목표 동작·현재 코드 동작·제안·미정을 구분합니다. 코드와 다르다는 이유로 확정 정책을 임의로 바꾸지 않으며, 문서 작성 자체를 실제 연동·검증 완료로 취급하지 않습니다. 남은 문서 갱신은 범위·담당과 함께 기록합니다.

3. 기획서에서 백엔드 요구사항 도출

Figma(기획서)는 사용자의 행위와 화면 상태를 보여주는 기획 근거입니다. 백엔드에서는 이를 도메인 규칙, 데이터 소유권, 상태 전이, 권한, API 동작으로 구체화합니다. 화면 필드가 곧 DB 컬럼이나 API 응답 필드가 되는 것은 아닙니다.

AI는 관련 화면·주석·프로토타입과 기존 결정을 대조해 부족한 설명과 결정할 항목을 찾습니다. 확인한 노드·날짜·범위를 남기고, 근거가 없는 내용은 미확인·충돌·접근 불가로 구분합니다.

예를 들어 중복 사용 규칙이 없으면 “어떤 요청을 동일 건으로 볼 것인가, 이미 처리된 요청은 어떤 결과를 반환할 것인가”를 질문합니다. 질문에는 변경 API·데이터 제약·경합 테스트에 미치는 영향과 결정 담당을 함께 남깁니다.

기획 보완 코멘트 — 사람·AI 공통 양식

기획서에서 확인되지 않는 정책·조건·분기가 있으면 해당 화면에 코멘트로 보완을 요청합니다. 사람이 직접 작성해도 되고, AI에게 초안이나 실제 게시를 요청해도 아래 형식을 사용합니다. 먼저 관련 화면·설명·기존 코멘트에서 답을 찾고, 함께 결정할 한 가지 주제씩 정리합니다.

작성 기준질문과 함께 기획서에 반영할 내용까지 명시합니다

‘내용이 부족합니다’에서 끝내지 않고 어떤 상황의 정책을 결정해야 하는지, 어느 흐름·상태 설명에 무엇을 추가해야 하는지, 개발에 어떤 영향이 있는지를 전달합니다.

[기획 보완 요청] <기능> — <결정할 항목> 대상: <화면명·노드 링크> 현재 확인: <관련 화면·설명에서 확인한 내용> 확인 요청: <실제 상황과 결정할 질문> 기획서 반영 요청: <추가할 정책·조건·분기·상태 설명> 개발 영향: <영향받는 API·데이터·테스트, 진행·보류 범위> 협의 대상: <결정할 역할·담당자, 모르면 확인 필요>

실제 담당자는 확인된 경우에만 지정하고, 모르면 ‘담당 확인 필요’로 남깁니다. 관련 결정 ID가 있으면 연결합니다. 공통 원본과 후속 기록 기준은 decisions.md에 있습니다.

작성 예시 · 실제 검토 결과나 확정 정책이 아닙니다

[기획 보완 요청] 이용권 사용 — 중복 요청 처리 대상: 이용권 사용 화면 / <실제 화면·노드 링크> 현재 확인: 사용 동작은 있지만, 검토한 화면·설명에서 중복 처리 기준을 찾지 못했습니다. 확인 요청: 같은 이용권의 사용 요청이 동시에 오거나 처리 후 재시도될 때 각각 어떤 결과를 반환해야 하나요? 기획서 반영 요청: 허용 결과, 오류·안내, 재시도 기준을 사용 흐름 설명에 추가해 주세요. 개발 영향: 변경 API·데이터 제약·트랜잭션·테스트에 영향을 줍니다. 해당 동작의 구현은 결정 후 진행하고, 기존 코드 조사와 설계 대안 검토는 진행할 수 있습니다. 협의 대상: 기획·운영 정책 담당과 백엔드 협의 필요 / 실제 담당 확인 필요

사람이 직접 남기거나 AI에게 요청하는 방법

  1. 직접 작성: 대상 화면에서 코멘트 기능을 선택하고 관련 위치에 핀을 둡니다. 양식에 맞춰 작성하고, 같은 질문이 이미 있으면 기존 스레드에 이어서 남깁니다.
  2. AI 초안: 화면 링크와 검토 범위를 주고 공통 양식으로 초안을 요청합니다. 초안만 요청하면 실제로 게시하지 않습니다.
  3. AI 게시: 게시할 대상·범위를 지정해 요청합니다. AI는 도구의 게시 기능·계정 권한을 확인한 뒤 등록하고 실제 코멘트 링크 또는 ID를 결과로 남깁니다. 게시할 수 없으면 초안과 필요한 설정을 제공해 사람이 등록하도록 합니다.

AI에게 초안 요청

Figma(기획서): <대상 화면·노드 링크> 검토 범위: <기능·흐름> lounge-grill과 공통 코멘트 양식을 사용해 기획 보완 코멘트 초안을 작성해줘. 관련 화면·설명·기존 결정·코멘트에서 먼저 답을 찾고 중복 질문은 제외해줘. 결정할 질문, 기획서 반영 요청, 개발 영향·담당을 포함해줘. 아직 게시하지 마.

AI에게 게시 요청

Figma(기획서): <대상 화면·노드 링크> 게시할 내용: <게시할 코멘트 본문 또는 이번에 검토할 범위> 공통 양식으로 기획 보완 코멘트를 작성해 해당 화면에 게시해줘. 기존 코멘트와 중복을 확인하고, 게시 결과와 코멘트 링크 또는 ID를 남겨줘. 게시 도구·권한이 없으면 초안과 필요한 설정을 알려줘. 게시한 것으로 처리하지 마.

게시 기능과 권한: 기획서를 읽는 MCP가 연결돼 있다는 사실만으로 코멘트 게시도 가능하다고 가정하지 않습니다. REST API를 쓰는 도구라면 기존 코멘트 조회는 file_comments:read, 게시는 file_comments:write가 필요하며 실제 파일 권한도 확인합니다. 공식 Comments API · 권한 범위

답변 이후: 결정자·답변·적용 범위와 코멘트 링크를 결정 기록에 연결하고, 기획서 반영 여부와 관련 작업의 재개 조건을 갱신합니다. 코멘트를 남긴 상태, 정책이 확정된 상태, 구현이 완료된 상태를 구분합니다.

4. 미정 정책과 작업 범위

업무상 허용 행위는 기획·운영과, API·이벤트 계약은 소비자·연동 담당과 확인합니다. 합의된 규칙을 만족하는 모델·트랜잭션·동시성 제어는 백엔드 개발자의 설계 영역입니다.

미정은 결정 기록에 질문·담당·개발 영향·재개 조건으로 남깁니다. 영향받는 부분만 보류하고 독립적으로 구현·검증할 수 있는 범위는 진행합니다. 이 판단은 설계와 구현 안에서 처리합니다.

확인미정 정책이 데이터 모델에 미치는 영향까지 확인합니다

독립된 조회 요구가 확인됐다면 해당 작업은 먼저 진행할 수 있습니다. 반면 상태 전이가 미정이면 변경 API와 저장 모델도 영향을 받습니다. 독립 검증이 가능한지 판단한 뒤 작업을 분리합니다.

API·스키마 초안은 합의된 사양과, 테스트 대체물은 실제 연동 결과와 구분합니다.

스킬은 요청 유형별 절차와 산출물을 정리한 실행 지침입니다. 기획 검토·설계와 작업 계획·구현과 검증·리뷰의 네 역할만 둡니다.

스킬에 무엇을 맡기고 어떤 결과를 받는가

스킬은 AI가 확인할 자료·판단 기준·예외 처리·결과 형식을 정의합니다. 요청할 때 대상 기능, 기획서·기존 문서·소스의 위치, 원하는 결과와 허용 범위를 함께 지정합니다. 네 단계를 매번 모두 실행할 필요는 없습니다. 기획 자료가 부족하면 기획 검토부터, 범위가 명확한 결함 수정은 구현·검증부터 시작할 수 있습니다.

기획 검토 · lounge-grill

개발 전에 무엇을 결정해야 하는지 찾습니다. Figma(기획서)·PPT·기존 docs와 현재 동작을 대조해 확인된 요구, 정책 질문, 계약 협의, 기술 설계를 구분합니다. 자료를 읽지 못한 것과 기획에 없는 것을 구분하며, 영향이 큰 질문부터 담당·진행 범위와 연결합니다.

요청 예시

대상: <기획서·기존 정책·API 명세 위치> 범위: <기능·화면·슬라이드> lounge-grill로 확인된 요구와 결정할 질문을 정리해줘. 근거·담당·개발 영향·진행 가능한 범위와 미확인 자료를 구분해줘. 아직 구현하지 마.

받을 결과: 확인된 요구·결정 질문·근거·영향·진행/보류 범위. 필요한 결정이 확인되면 설계로 연결합니다.

설계·작업 계획 · lounge-spec

확인된 요구를 기존 코드 구조에서 구현 가능한 계획으로 바꿉니다. API·데이터·트랜잭션과 소비자 영향을 함께 보고, 필요한 대안의 선택 이유와 검증 가능한 작업·선행 조건을 정합니다. 문서 작성만으로 구현이나 배포가 시작되지는 않습니다.

요청 예시

저장소: <백엔드 경로> 요구·결정: <관련 문서·결정 ID> lounge-spec으로 기존 구조를 확인하고 변경 위치·설계 이유·호환성 영향을 정리해줘. 작업별 선행 조건·완료 조건·검증과 남은 미정을 계획해줘. 이번 요청은 설계까지야.

받을 결과: 현재 구조·변경 설계·선택 이유·작업 계획·검증 조건. 구현에 필요한 근거와 제약을 넘깁니다.

구현·검증 · lounge-implement

허용된 작업 범위에서 코드를 수정하고 실제 저장소 명령으로 검증합니다. 관련 호출자·테이블·외부 처리까지 영향을 확인하고, 변경 유형에 필요한 테스트를 선택합니다. 새 정책이 필요하면 관련 부분과 독립 작업을 구분하고, 실행하지 못한 검증도 결과에 남깁니다.

요청 예시

저장소: <백엔드 경로> 작업: <작업 기록·확인된 범위·완료 조건> lounge-implement로 해당 범위를 구현하고 관련 테스트를 실행해줘. 정책·계약 충돌이 발견되면 영향과 진행/보류 범위를 정리해줘. 변경 파일·실제 검증 결과·미검증·다음 작업을 남겨줘.

받을 결과: 변경 코드·계약·데이터·문서 영향, 검증 환경·명령·결과, 완료 조건과 남은 작업. 필수 검증이 남으면 전체 완료로 표시하지 않습니다.

리뷰 · lounge-review

설계나 실제 변경이 요구를 충족하는지 검토합니다. 정상 동작 외에도 권한·정합성·경합·실패·재시도·소비자 호환성을 추적합니다. 실제 결함, 미정 정책, 개선 제안과 검증 한계를 나눠 근거를 제시합니다.

요청 예시

대상: <설계 또는 diff·변경 파일·비교 기준> 요구·검증: <관련 결정·완료 조건·테스트 결과> lounge-review로 결함을 검토해줘. 위치·발생 조건·영향·수정 방향을 제시하고 미정·미검증과 구분해줘. 코드는 수정하지 마.

받을 결과: 우선순위별 결함·근거, 결정 질문, 확인한 검증과 한계, 완료 조건별 판단. 결함이 없으면 없다고 보고합니다.

하나의 기능이 네 단계를 지나는 예시

구현·검증허용된 범위를 구현하고 정상·중복·권한·경합을 확인합니다. 실제 DB 경합 검증을 실행하지 못했다면 Not Run과 필요한 환경을 남깁니다.변경 코드·실제 검증 근거·미검증·완료 조건 충족 여부
리뷰동시 요청이 상태 변경을 중복 수행할 수 있는지 코드·DB 제약·트랜잭션을 추적합니다. 성립하는 결함과 단순 미검증을 구분합니다.위치·발생 조건·영향·수정 방향, 재검증할 항목

위 흐름도와 함께 보면 질문이 설계 조건으로, 설계 조건이 코드·검증으로, 검증 근거가 리뷰로 이어집니다. 새 정책이 발견되면 필요한 결정으로 돌아가되 모든 단계를 처음부터 반복하지 않습니다. 각 스킬 파일에는 입력·판단·예외 처리와 결과 양식이 있습니다. 상세 개발 기준은 기존 개발 기준에서 필요한 절만 연결합니다.

6. 구현·검증·인수인계

작업의 완료 조건은 관찰 가능한 서버 동작으로 정의합니다. 이용권 사용 기능이라면 합의된 상태 전이·권한·중복 처리 규칙이 정상 요청뿐 아니라 실패·재시도·동시 요청에서도 유지되는지 확인하는 식입니다. 구체적인 처리 결과는 확정 정책을 따릅니다.

변경 대상선택할 검증
도메인 로직상태 전이·경계 조건·권한에 대한 단위 테스트
영속화·스키마실제 DB 특성을 반영한 제약·트랜잭션·rollback·경합, 마이그레이션 호환성 검증
API 계약입출력·인증/인가·오류·멱등성, 기존 소비자 호환성 검증
외부 연동·이벤트타임아웃·중복·부분 실패·재처리와 실제 연동 환경 확인

모든 작업에 모든 검증을 요구하지는 않습니다. 실제 저장소의 빌드·정적 검사·테스트 명령 중 변경 영향에 필요한 것을 실행하고, 대상·환경·결과를 Pass / Fail / Not Run / N/A로 남깁니다. Mock이나 대체 DB에서 통과한 결과는 실제 환경 검증과 구분합니다.

확인필수 검증이 남아 있으면 완료로 표시하지 않습니다

Done은 작업 카드에 명시한 범위의 완료입니다. 단위 테스트 통과·실제 DB 검증·외부 연동 확인·배포 완료를 구분합니다.

작업 기록에 변경 코드·스키마·계약, 검증 근거, 남은 결정·배포 순서·운영 확인과 다음 담당을 남깁니다.

7. 개인 하네스 연결

팀이 공유하는 것은 규칙·스킬·결정·작업 기록입니다. 각 개발자는 사용하는 AI 도구에 PPT 등 파일·Figma(기획서) 읽기, 코드 검색, 빌드/테스트 실행을 연결합니다. 첫 기획서 읽기는 시작 절의 순서로 확인합니다. 이 연결과 실행 환경을 여기서는 하네스라고 부릅니다.

처음에는 공용 AGENTS.md와 필요한 SKILL.md를 직접 읽게 하면 됩니다. 자동 등록은 개인 환경에서 구성하고, 복사해서 쓸 때는 폴더 구조와 상대 경로를 유지합니다. 작은 실제 작업 하나로 자료 읽기부터 결과 기록까지 연결되는지 확인합니다.

사용 시 주의하네스·스킬은 실제 작업에서 확인하며 보완해야 합니다

지침과 연결 설정만으로 AI의 임의 판단이 자동 차단되거나 모든 기획 누락이 발견된다고 보장하지 않습니다. 처음 연결할 때와 AI 도구·연결·지침 변경 후에는 작은 실제 작업으로 확인하고, 사용 중 드러난 문제를 수정합니다.

  • 적용한 지침과 읽은 자료가 결과의 근거에 연결되는지 확인합니다.
  • 불분명한 정책을 임의 확정하지 않고 질문·담당·개발 영향·진행/보류 범위를 남기는지 봅니다. 자료 접근 실패와 기획 누락도 구분해야 합니다.
  • 결정 기록이 다음 설계·구현에 반영되는지 확인합니다. 근거 없는 정책·경로·완료 보고가 나오면 영향받는 결과를 재검토하고 자료 연결·개인 하네스·공통 스킬 중 원인을 보완합니다.
  • 보완 후 같은 조건에서 필요한 범위를 다시 확인하고 미검증을 남깁니다. 이 확인은 제품 코드·DB·외부 연동 검증을 대신하지 않습니다.

상세 기준은 사용 중 검증·보완을 참고합니다.

처음 요청할 때는 도입부의 시작 프롬프트를 사용합니다. 기록 위치와 갱신 방법은 공유 기록·가이드 갱신 기준을 따릅니다.
